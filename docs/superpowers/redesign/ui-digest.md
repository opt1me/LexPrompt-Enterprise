# LexPrompt Redesign — UI Digest

Source: `design_handoff_lexprompt_redesign/LexPrompt Redesign.dc.html` (2084 lines) and `LexPrompt Current.dc.html` (609 lines). The redesign file is structured as a sequence of design "turns" (t0–t4), each turn containing several labelled screen options (e.g. `1a`, `1b`…). t0 is just a link back to the current-app recreation; t1–t4 are the actual redesign proposals. This digest treats every lettered option as a screen/mockup and calls out which are alternates for the same slot vs. genuinely distinct views.

---

## 1. Screen inventory for the REDESIGN

### Turn 1 — core shell and review

**1a — Matter home ("status board")**
- Purpose: top-level landing page for a single matter; answers "how much of this is actually checked by a human" before anything else.
- Layout: persistent top bar (logo "LexPrompt" + firm tag "CH&P LLP", nav tabs `Matters / Playbooks / Standard positions`, search box with `⌘K` hint, settings icon, user avatar initials). Below it, a left rail listing matters ("Meadowview — Unit 14", "Riverside portfolio (11 ASTs)", "Foxglove NDA bundle", "Kilnhouse assignment") each with a one-line status ("24 of 42 verified", "complete", "2 flagged", "Draft · no run yet"), plus an "Assigned to me" counter (badge "6") pinned at the bottom. Main pane: matter header (matter number "MATTER 24-0871", status pill "IN REVIEW", title, client/role line), action buttons `Export report` / `New review`; a 3-up stat row — "Verification progress" (24/42, stacked bar, legend: verified/flagged/rejected/unchecked), "Needs attention" (counts: flagged for follow-up, deviate from standard position, unassigned/no owner), "Risk profile" (High/Med/Low bars with counts); a 2-column area below with "Documents & collections" (list, including a "Lease as varied" **collection** card showing BASE/VARIES rows) and "Reviews" (run history with spinner/checkmark status, "Open review →" / "Archived") on the left, "Activity" feed (verify/flag/reject/run events, actor, timestamp) on the right.
- Primary actions: switch matter (left rail), `Export report`, `New review`, `Add` documents, open a review, open activity items.
- IA: Matter is the top-level container; nests Documents & Collections, Reviews (each review = one playbook run over the matter's docs), and Activity. This is new — there is no equivalent "matter" object today.

**1b — Review screen, "the ledger" (three-pane)**
- Purpose: work through findings clause-by-clause with document evidence visible at all times. One of two alternate designs for the review/verification screen (see 1c).
- Layout: top bar (back chevron, matter+playbook title, clause/doc/run-date meta, segmented control `Review / Compare / Report`, `Export`). A banner below when findings are unchecked ("10 findings are unchecked. Export is available, but the report will mark them as unverified AI output." + "Review unchecked →"). Three columns: (1) 258px clause index — a "Lease as varied" collection selector, count chips (HIGH/FLAGGED/UNCHECKED), then a scrollable list of clauses each showing an icon (verified/flagged/rejected/unchecked/extracting/queued), number, title, and status subtext ("verified · low", "flagged · high · deviates", "net position confirmed", "rejected by M. Okafor"), with a progress bar+fraction footer ("13/18"); (2) 470px finding detail — clause number/risk/flag badges, title, "FINDING" prose paragraph with an "Edited by you · <timestamp>" / `Edit` line, "EVIDENCE — N PASSAGES" block of quoted excerpts each tagged with source doc + page + clause ref and a `Show in document` link, an "AGAINST OUR STANDARD POSITION" box (only when applicable) with a `DEVIATES` badge and a two-column "WE ASK FOR" vs "THIS LEASE SAYS" comparison, a private "NOTES" block with avatar + free text; a sticky bottom "DISPOSITION" bar with `Verify` / `Flagged` / `Reject` buttons, an assignee chip, `Note`, and "Next unchecked → (J)" keyboard-shortcut hint; (3) document pane — tabs per source document (LEASE / DEED OF VARIATION / LICENCE TO ALTER), page indicator + zoom/search icons, a rendered page mockup with the cited passage highlighted (yellow wash + underline), and a footer "Passage 1 of 2 for this clause" with Prev/Next.
- Primary actions: verify/flag/reject a finding, assign an owner, add a private note, edit the finding text, jump to next unchecked (keyboard shortcut `J`), navigate between evidence passages, switch documents, export.

**1c — Review screen, "the brief" (single column)**
- Purpose: same underlying data as 1b, but as one continuously scrolling document-like feed ("reads like a written advice note"), with the PDF opening as an on-demand overlay instead of a permanent pane. Explicitly stated to be the same layout mobile gets, and framed as alternative to 1b (only one is expected to ship).
- Layout: top bar (back, title, `Unchecked only` filter toggle, `Export`). Centered 760px column: header ("Findings — lease as varied", summary counts, progress bar+fraction) then a stack of per-clause cards, each with number, title, risk/flag badges, finding prose, an indented italic evidence quote with inline doc/page/clause reference chips (multiple docs shown side by side, e.g. "LEASE p.14 cl.5.2" and "DOV p.3 cl.2.1"), a "Deviates from standard" callout, and inline action row (`Verify`, `Flagged`, `Edit`, `Note (n)`, `Open in document`). Includes a rejected-finding card with a `Re-run` action and an in-progress card with a pulsing skeleton bar ("extracting…").
- Primary actions: same verify/flag/reject/edit/note/open-document/export/filter set as 1b, but scoped per card in a single scroll rather than split panes.

**1d — The collection detail / "variation trail" modal**
- Purpose: for one clause governed by a base document plus amendments, show the derivation of the "net position" the lawyer must confirm, rather than asserting it silently.
- Layout: modal header ("Lease as varied", "clause 4 of 18", close). Body: a vertical timeline — "ORIGINAL" node (doc name, date, prose, indented italic quote + citation), "VARIED BY" node (doc name, date, prose describing the change, quote + citation, distinguishing highlight color), and a terminal "NET POSITION" card (synthesized prose with bolded key terms, and a `Net position confirmed` action button with attribution "by R. Hume, <timestamp>" plus an `Amend` link).
- Primary actions: `Confirm net position` / `Amend`; step through the trail; this is the drill-down invoked from a "see the variation trail" link elsewhere (e.g. 1c clause 04).

**1e — Comparison grid**
- Purpose: cross-document comparison for a portfolio of genuinely separate documents (e.g. 11 ASTs) rather than one lease with variations — the redesign's replacement for today's Tabular Review. "Risk reads down a column, verification reads across a row, and the cell is a sentence rather than a truncated blob."
- Layout: top bar (back, portfolio title + playbook/doc-count meta, `High risk only` filter, `Full text` toggle, `Export`). A `table-layout:fixed` table: header row shows clause name per column plus a stacked mini risk-distribution bar (red/amber/green segments) summarizing that clause across all rows; body rows are one per document, first column showing document name + a status chip (`2 HIGH` / `CLEAR` / `1 FLAGGED` / `queued`) and "n/9 verified"; each data cell shows a risk dot+label (HIGH/MED/LOW), a verification icon (check/flag/empty circle), and a short full sentence (not truncated) of the finding; the "selected" cell carries a distinguishing inset border. A queued/未-run row renders all cells as em-dashes at reduced opacity. Bottom bar shows the currently selected cell's document+clause and action buttons `Verify` / `Flag` / `Open in review`.
- Primary actions: filter to high risk, toggle full text, select a cell to act on it (verify/flag/open in review), export.

**1f — First run / new-matter intake**
- Purpose: replace "build a template before anything happens" with "name a matter, drop documents, and the app tells you what it thinks they are" — playbook choice comes last and is pre-answered by AI suggestion.
- Layout: top bar with a 3-step tracker (`1 MATTER / 2 DOCUMENTS / 3 PLAYBOOK`). Body: prompt "What are we reading?"; a dashed drop-zone containing an auto-detected **collection** card ("Lease as varied — Read together as one position · 3 documents", `Ungroup` action) listing BASE/VARIES rows, one of which is mid-OCR ("Scanned — running OCR, 40%" with a scan icon); a standalone document row with an `Add to a group` action; an AI suggestion banner ("These look like a commercial lease acting for the tenant. Your Commercial Lease — Tenant v4 playbook fits…") with `Use it — start review` / `Choose another` / `Draft a new playbook`; footer privacy note ("Documents stay in your browser. Only extracted text is sent to the model you chose.") and a model-selection link.
- Primary actions: group/ungroup documents into a collection, add documents, accept/override the suggested playbook, choose model, start review.

**1g — Playbook editor (steady state)**
- Purpose: the redesign's Template Editor equivalent — a saved playbook viewed/edited outside of the authoring flow.
- Layout: top bar (back, playbook title + version/usage meta "v4 · 18 clauses · used in 7 matters · edited 19 Aug", `View prompt`, `Save v5`). Left rail (288px): "Acting for" tenant/landlord toggle, "House style" persona text block, "Risk appetite" text block, and a footer stat "6 of 18 clauses have a standard position" with a progress bar. Main pane: clause list, each card showing drag handle, number, title, a `HAS STANDARD POSITION` / `NO STANDARD POSITION` badge, and (when expanded) three stacked fields — `EXTRACT` (instruction), `RISKY WHEN` (risk criteria), and `OUR STANDARD POSITION` (new field — the firm's house position, absent from the current app).
- Primary actions: edit acting-for/house-style/risk-appetite, add/reorder/expand clauses, edit the three per-clause fields, view raw prompt, save a new version.

**1h — Mobile (three screens, explicitly "full parity, not a cut-down")**
- Screen 1: matter board — status bar mock, header with matter number + title, a compact verification-progress card, a "NEEDS YOU" list of finding cards (badges, title, assignment note), and a bottom tab bar (`Matters` / `Assigned` / `Playbooks`).
- Screen 2: single finding — same content as one card from 1b/1c (badges, title, finding prose, one evidence quote with a tap-through citation chip, deviates-from-standard callout, note-with-avatar), with a pinned bottom action bar (`Verify` full-width + icon-only `Flag`/`Reject`/`More`) and prev/next clause navigation.
- Screen 3: variation trail — same timeline content as 1d, condensed for mobile width, with a pinned `Confirm net position` button.
- These are responsive treatments of 1a, 1b/1c, and 1d — not new IA.

### Turn 2 — playbook authoring

**2a — New playbook (three routes)**
- Purpose: entry point for creating a playbook; explicitly frames three routes as parallel, not a fork.
- Layout: header (back, "Playbooks · new"). Three route cards: "Draft it with AI" (selected/highlighted), "Learn from past documents" (link to turn 3), "Build it by hand" (link to 2c). Below, a form (shown in the AI-selected state): Contract Type field, "Acting for" Tenant/Landlord toggle, a free-text "What matters on this kind of deal" textarea, a "LEARN FROM" checklist letting the user select existing playbooks and **signed-off matters** as few-shot style sources (checked: "Commercial Lease — Tenant v4" playbook, "Kilnhouse assignment" matter; unchecked and flagged as mismatched: "Riverside portfolio — 11 ASTs … residential, different animal"), and two segmented controls: "How many clauses" (Key terms ~8 / Standard ~18 / Full report ~30) and "Answer length" (A line / A paragraph / Full note). Footer: "Nothing is saved until you have been through the draft." + `Cancel` / `Draft the playbook`.
- Primary actions: pick a route, fill contract type/role/context, select prior playbooks/matters to learn house style from, choose clause density and answer verbosity, generate a draft.

**2b — AI first-pass draft (pre-save review)**
- Purpose: the important screen per the design notes — an AI first pass is a **draft**, never a saved playbook, until the lawyer has gone through every clause.
- Layout: header shows "UNSAVED DRAFT" badge, provenance meta ("drafted from 1 playbook + 1 signed-off matter · claude-sonnet-4 · 19 clauses proposed"), a progress bar+fraction ("9/19 reviewed"), `Discard` / `Save as v1` (disabled/gated language implied). A banner: "This is a first pass. Keep what is right, rewrite what is nearly right, cut the rest. Ten clauses still need a look." + "Go to next unreviewed →". Left rail (250px): status chips (`7 KEPT` / `2 CUT` / `10 NEW`) then the clause list with per-row icons (kept=check, cut=struck-through x, new/unreviewed=circle, current=sparkle+highlight), plus "Add a clause of my own". Main pane, per clause: header ("CLAUSE 3 OF 19", "AI DRAFTED — NOT YET REVIEWED" badge), title, `EXTRACT` field with a `Rewrite` action, two-column `RISKY WHEN` / `OUR STANDARD POSITION` (the latter shows provenance: "Taken from Commercial Lease — Tenant v4"), an "ALSO SUGGESTED" box offering optional sub-questions with `Add` / `Dismiss` per suggestion, and a footer action row `Keep this clause` / `Edit then keep` / `Cut`, plus a keyboard-shortcut hint (`Next (J)`).
- Primary actions: per clause — keep, edit-then-keep, cut, add suggested sub-question or dismiss it; globally — discard the whole draft, save as v1 once reviewed.

**2c — Build by hand (with per-field AI assist)**
- Purpose: show that manual authoring and AI drafting interleave at the field level rather than being separate products.
- Layout: header ("Untitled playbook", "UNSAVED DRAFT" badge, "built by hand · 2 clauses", `Save as v1`). Body: a collapsed clause row ("WRITTEN BY YOU" badge) and an expanded clause editor with drag handle/number/title, and three fields each independently authorable: `EXTRACT` with a `Draft this for me` link; `RISKY WHEN` shown *already AI-suggested* (dashed border) with a `SUGGESTED` badge and `Use this` / `Try again` / `I'll write it` controls; `OUR STANDARD POSITION` shown empty with placeholder text and a note "optional — enables 'deviates' flagging". Footer: `Add another clause` / `Suggest what I'm missing`.
- Primary actions: add clauses, request AI draft per field, accept/regenerate/reject an AI suggestion per field, save as v1.

### Turn 3 — learning a playbook from redlines

**3a — Bring in the precedent (document intake for learning)**
- Purpose: ingest past negotiated documents (not a description) as the source of a playbook's standard positions.
- Layout: header with a 3-step tracker (`1 DOCUMENTS / 2 WHAT WE LEARNED / 3 DRAFT`). Body: prompt "What have you negotiated before?"; a "chained" document group card ("Ashgrove Unit 6 — 3 turns", badge "CHAINED · STRONGEST SIGNAL", subtitle "first draft → our markup → executed") listing TURN 1 (their draft), TURN 2 (our markup, "tracked changes found · 84 edits"), TURN 3 (executed, page count + signed date); a "Standalone precedent" group card listing individually-tagged documents (OUR MARKUP / EXECUTED chips) plus one **ambiguous** document with a "What is this?" prompt and three manually-selectable role chips (THEIR DRAFT / OUR MARKUP / EXECUTED); a drop zone for more documents; footer summary ("7 documents · 1 chain · 146 tracked edits to read") and `Back` / `Read the redlines`.
- Primary actions: classify document roles (chain vs. standalone, and per-doc role when ambiguous), add more documents, proceed to have the model read tracked changes and comments.

**3b — What we learned (inferred positions review)**
- Purpose: surface AI-inferred standard positions from redlines as claims with basis and confidence, for explicit accept/soften/reject — never auto-adopted.
- Layout: header ("NOTHING SAVED YET" badge, meta "7 documents · 146 tracked edits · 14 positions inferred, 3 open questions", a segmented decided/rejected progress bar "6/14 decided", `Build the playbook`). An info banner: "These are observations about what you did, not advice. A position you struck once is a weak signal; one you struck every time is your house rule." Body: "SORTED BY STRENGTH" header with `Accept all consistent (5)` bulk action, then position cards with a strength badge (`CONSISTENT · 4 OF 4`, `MIXED · 2 OF 4`, `ONE INSTANCE · WEAK`), an "INFERRED POSITION" prose statement, a "BASIS" list of per-document evidence bullets (struck/kept icons + document names), a warning callout for contradictory evidence ("The redlines contradict each other here. Worth deciding deliberately rather than inheriting."), and an action row `Adopt as standard position` / `Reword` / `Not a house rule` / `See the N redlines`. A distinct "OPEN QUESTIONS" box lists things the redlines could not settle (e.g. "Every lease you sent had a break clause, but you never amended one. Do you have a position?") with `Answer` / `Skip` per question.
- Primary actions: per position — adopt, reword, reject ("not a house rule") or, for mixed evidence, "Adopt"/"Write my own"/"Just extract it, no position"; answer or skip open questions; bulk-accept consistent positions; proceed to build the playbook.

**3c — The workings (evidence drill-down for one position)**
- Purpose: show the actual redline text behind a single inferred position, because "a lawyer will not adopt a position they cannot see the workings for."
- Layout: header ("Rent review — the workings", "· 6 redlines across 4 documents", close). Body: the inferred-position statement restated at top; then a list of per-document evidence blocks — a markup excerpt rendered with **struck-through deleted text and underlined inserted text inline in the same sentence**, tagged with role/document/turn and a clause/page ref, plus (when present) a **margin comment** rendered as an avatar-initialed callout with the actual comment text and date; an executed-document excerpt with the operative language highlighted; collapsed rows for additional documents (expandable, "chevron-down"). Footer: `Adopt as standard position` / `Reword first`, and a privacy note: "Precedent documents are read once and are not stored with the playbook."
- Primary actions: expand/collapse per-document evidence, adopt or reword the position from here directly.

### Turn 4 — keeping a playbook current

**4a — Living playbook page**
- Purpose: make staleness of a "standard position" visible rather than presenting it as permanently authoritative.
- Layout: header (back, title, version/usage meta "v4 · 18 clauses · 6 standard positions · used in 7 matters", `History`, `Teach it a new deal`). A drop zone: "Drop in a newer turn — A marked-up draft or an executed lease from a deal since v4. LexPrompt reads it against the positions below and proposes changes." / "or pull from a signed-off matter". "Standard positions" list (6 of 18 clauses shown), each row showing the position text and a **staleness/evidence badge**: `HELD 5 OF 5` (green, with "learned from 6 redlines" / "last tested 3 weeks ago · Ashgrove" / a `Workings` link), `CONCEDED TWICE SINCE` (amber, with a warning callout "You have signed two leases since v4 without this exclusion. The position may no longer be one." + `Review`), `UNTESTED 18 MONTHS` (greyed, "no deal has tested it since Feb 2025"), and a bare "NO POSITION — EXTRACT ONLY" row with `Add one`.
- Primary actions: feed a new deal/document in to re-test positions, open "workings" evidence, review/confirm a drifting position, add a position to an extract-only clause, view version history.

**4b — The changeset (proposed edits to a live playbook)**
- Purpose: turn a new negotiated document into an explicit, reviewable diff against the current playbook version rather than silently rewriting it.
- Layout: header shows version transition chip "v4 → v5 PROPOSED", source line ("read from Brookvale Retail Park — our markup + executed, Jul 2026 · 7 proposed changes"), a running tally ("3 accepted · 1 declined · 3 open"), `Discard` / `Publish v5 (3 changes)`. A category-count row: `2 CONFIRM` / `2 DRIFT` / `3 NEW CLAUSE`, plus "Nothing changes in v4 until you publish." Body: change cards by type — **DRIFT** (side-by-side "V4 SAYS" vs "PROPOSED FOR V5" text, a "WHY" bulleted rationale citing specific deals, actions `Take this change` / `Reword it` / "Keep v4 — that was a trade, not a change of policy" / `See the redlines`); **NEW CLAUSE** (prose explaining why this clause has never been covered, proposed clause number and standard position, actions `Add clause 19` / `Add it, but no position` / `Skip`); **CONFIRM** (compact row, "Held again — evidence 5 of 5 → 6 of 6", already marked `Accepted`); a **declined** DRIFT row shown dimmed/struck-through with `Declined`.
- Primary actions: per proposed change — accept/take, reword, decline/keep old, view underlying redlines, add or skip a new clause; discard or publish the whole changeset (only the accepted subset publishes).

**4c — Version history**
- Purpose: let a finding from months ago still be read against the playbook version that actually produced it.
- Layout: header (back, title, "· history"). A vertical timeline: v4 (current, filled dot) with author/date, a changelog list (icons: plus-circle for added clauses, scale for position changes) and a footer ("used in 4 matters", `Compare to v3`); v3, v2 similarly (outline dots) each with a one-line changelog and matter usage/names; v1 as a terminal minimal entry ("drafted with AI, tailored by R. Hume").
- Primary actions: open a `Compare to v<n>` diff (not itself rendered as a screen — implied), browse version changelogs.

## 2. Navigation model

- **Top-level object is the Matter**, not a template/run. Matters replace the current app's implicit "session" — reviews, documents, and activity all nest under a matter and persist.
- **Entry point**: the Matters list (left rail on 1a) with a global top nav offering three sections as tabs: `Matters`, `Playbooks`, `Standard positions` (the last is named but no screen for it is drawn — see §7). A `⌘K` search box searches "matters, clauses, findings" globally.
- **Persistent chrome**: the top bar (logo + firm name "CH&P LLP", the three nav tabs, search, settings, user avatar) appears on every desktop screen. Inside a matter, a left rail lists sibling matters plus an "Assigned to me" counter; inside a review (1b), a left rail instead lists that review's clauses; inside a playbook, a left rail shows playbook-level fields (1g) or the review-progress rail (2b).
- **Per-screen content**: everything right of/below the persistent chrome is the current view — matter dashboard (1a), review workspace (1b/1c), collection drill-down (1d, presented as a modal/overlay over the review), comparison grid (1e), intake wizard (1f, 3-step), playbook editor (1g), playbook authoring wizard (2a→2b or 2a→2c, both step-tracked), playbook-learning wizard (3a→3b→3c drill-down), and playbook-maintenance screens (4a→4b changeset, 4c history).
- **Within a review**, a segmented control switches between `Review` / `Compare` / `Report` modes (seen in 1b's header) — `Compare` presumably maps to something like 1e or a diff view, and `Report` to the exported client report; neither sub-mode is itself drawn out.
- **Mobile (1h)** collapses the top nav and left rails into a bottom tab bar (`Matters` / `Assigned` / `Playbooks`) and pushes clause-to-clause navigation into swipe/prev-next controls at the screen bottom; it mirrors desktop IA rather than removing levels.
- **Cross-links between flows**: 1f's AI playbook suggestion links directly into a review; 2a's "Learn from past documents" option links to turn 3's flow; 1c's "see the variation trail" opens 1d; 3b's "See the N redlines" opens 3c; 4a's "Teach it a new deal" opens 4b; 4a's `History` opens 4c.

## 3. Screen-by-screen diff against the current app

**Survive largely intact (same purpose, redesigned visually/informationally but not structurally new):**
- Template/Playbook library → replaced conceptually by the `Playbooks` nav tab (no library grid screen is drawn, but the object and "used in N matters" concept persists from `TemplateLibrary.tsx`).
- Template/Playbook editor: `TemplateEditor.tsx` (current) → **1g** Playbook editor. Same three-pane concept (persona/format/risk-tolerance sidebar + clause list) survives, with clause fields renamed (Extract / Risky when) and restyled.
- Settings panel (OpenRouter key, model picker, parallel-requests slider): no redesign screen appears anywhere in the file. Presumed to survive as-is or move under the settings gear icon in the top bar (unconfirmed — see §7).
- Run/upload flow: `RunPanel.tsx` (current, a single modal: drag-drop, file list, run button) → **1f** First run, same core mechanic (drop files, see readiness, hit run) but restructured as a 3-step wizard with document grouping and AI-suggested playbook.
- Tabular grid: `TabularReview.tsx` + `CellDetail.tsx` (current, docs × clauses table with a side detail/PDF panel) → **1e** Comparison grid. Same fundamental table shape, but redesigned to show full sentences per cell, a risk-distribution mini-bar per column header, and verification icons per cell; the side detail+PDF panel is dropped in favor of a bottom action bar plus `Open in review`.

**Change substantially:**
- Results view: `ResultsView.tsx` + `FindingCard.tsx` (current: 3-pane layout — folder-like doc switcher, card list of findings streaming in with loading skeletons/retry, and a PDF pane) → becomes **1b** (three-pane "ledger") or **1c** (single-column "brief"), presented explicitly as two alternative redesigns of the same slot. New elements not in the current cards: a persistent per-review verification-progress rail/bar, an explicit disposition workflow (Verify/Flag/Reject/Assign/Note, not just risk display), inline evidence citation blocks with per-document/page/clause tags (today citations are "Ref 1"/"Ref 2" chips that presumably open the PDF, with no quoted text inline), and a standard-position comparison box ("deviates").
- Create Template flow: `CreateTemplateDialog.tsx` (current: single modal with AI-Generator/Blank-Template tabs, contract type, depth/verbosity sliders) → becomes the multi-screen **2a→2b** (AI draft path, gated by a mandatory per-clause review before saving) and **2a→2c** (blank/by-hand path with per-field AI assist). The current dialog auto-generates and saves in one step; the redesign makes the AI output an explicit unsaved draft state that must be worked through.

**Entirely new (no equivalent in the current app at all):**
- **Matter** as a top-level object and **1a** Matter home dashboard (verification progress, needs-attention, risk profile, documents & collections, reviews, activity feed). Today, runs/results are not persisted as a named container.
- **Collections** ("read together as one position") and the **variation trail** (**1d**), showing a base document plus amending documents resolving to a lawyer-confirmed "net position."
- **Standard positions** as a first-class per-clause field (visible in 1g, 2b, 2c) and the **"deviates from standard"** comparison UI in 1b/1c/1h.
- **Verification/disposition workflow** — Verify / Flag / Reject / Assign-to / private Note per finding, with an aggregate verification-progress metric gating export ("10 findings are unchecked… the report will mark them as unverified AI output"). The current app has risk levels but no human sign-off state at all.
- **Playbook learning from redlines** — the entire turn-3 flow (3a document-role classification and chaining, 3b inferred-position review with strength/consistency scoring and open questions, 3c tracked-changes/margin-comment drill-down).
- **Playbook maintenance / drift detection** — the entire turn-4 flow (4a staleness badges on positions, 4b changeset review with CONFIRM/DRIFT/NEW CLAUSE categorization and per-change accept/decline, 4c version history with changelogs and per-version matter usage).
- **Comparison grid as portfolio tool** is new in spirit even though it visually descends from the tabular view — it's explicitly scoped to "genuinely separate documents" as distinct from the collection/variation-trail case, a distinction the current app does not make at all.
- Full mobile parity (**1h**) — the current app has no mobile treatment.

## 4. New UI concepts and components with no current equivalent

- **Verification state / disposition** — a finding-level status machine: `unchecked → verified | flagged | rejected`, each with an icon (`check-circle-2`, `flag`, `x-circle`, hollow `circle`), an optional assignee, and an optional private note. Shown at three granularities: per-clause in the left rail (1b), inline per-card (1c), and aggregated as a stacked progress bar + counts at the matter (1a) and review (1b) level. User actions: `Verify`, `Flagged` (toggle), `Reject`, assign an owner, add a note, "Next unchecked" keyboard shortcut (`J`).
- **Standard position / "deviates"** — each playbook clause can optionally carry a firm's "our standard position" (free text). When a finding disagrees, the UI renders an "AGAINST OUR STANDARD POSITION" / "DEVIATES" box with a two-column "WE ASK FOR" vs "THIS LEASE SAYS" comparison. This requires a diffing/matching step between the model's extracted finding and the stored standard-position text (semantic, not textual — the model itself would need to render the verdict, since the strings won't literally match).
- **Collections / variation trail** — a set of documents (one BASE + one or more VARIES) treated as a single logical clause source. Renders as: (a) a compact collection card (1a/1f) with BASE/VARIES rows, (b) a full timeline drill-down (1d/1h) showing per-document quoted excerpts plus a synthesized "NET POSITION" that must be explicitly "confirmed" by a named user. States: unconfirmed net position vs. confirmed (with confirmer name + timestamp) vs. "Amend."
- **Inline evidence citations with quoted text** — unlike the current app's "Ref 1 / Ref 2" chips (which presumably just scroll/highlight the PDF), the redesign always prints the actual quoted passage inline (italicized, in Newsreader serif) next to a small monospace tag (`LEASE · p.14 · cl.5.2`) and a `Show in document` / `Open in document` action. Multiple evidence passages per finding are numbered ("EVIDENCE — 2 PASSAGES") with prev/next stepping in the PDF pane's footer.
- **Tracked-changes rendering ("the workings", 3c)** — a single sentence rendered with live strikethrough (deleted text) and underline (inserted text) inline, sourced from Word/DOCX tracked changes, plus **margin comments** rendered as avatar-initialed callout bubbles with the original commenter's text and date. This is a genuinely new rendering primitive: current app has zero document-diff or comment-thread capability.
- **Document role classification** (3a) — documents get tagged `THEIR DRAFT` / `OUR MARKUP` / `EXECUTED`, and multiple turns of the same negotiation are "chained" together with an explicit ordering (turn 1 → 2 → 3) and a "strongest signal" badge. An ambiguous document surfaces a manual "What is this?" chip-picker.
- **Inferred position with strength/consistency scoring** (3b) — a claim ("You do not accept upwards-only review without a cap") tagged `CONSISTENT · 4 OF 4`, `MIXED · 2 OF 4`, or `ONE INSTANCE · WEAK`, with a bulleted "BASIS" evidence list drawn from multiple documents, and three-way resolution (`Adopt`, `Reword`, `Not a house rule`) rather than a binary accept/reject. A parallel **"open questions"** list surfaces things the evidence could not settle at all (distinct from low-confidence — these have no inferred answer to accept or reject).
- **Playbook staleness badges** (4a) — per-position badges: `HELD N OF N` (green, still true), `CONCEDED TWICE SINCE` (amber, drifting — with an explicit warning sentence and a `Review` action), `UNTESTED N MONTHS` (grey, no recent evidence either way), `NO POSITION — EXTRACT ONLY` (no position ever set). This requires tracking, per position, every matter/deal that has since tested it and whether the position held.
- **Changeset / diff-and-publish for playbooks** (4b) — a proposed new version (v5) is generated as a set of discrete, individually acceptable/declinable changes, each categorized `CONFIRM` / `DRIFT` / `NEW CLAUSE`, with only the accepted subset actually being published; publishing is versioned (v4 unchanged until publish) and the publish button is labelled with the count of changes actually taken ("Publish v5 (3 changes)").
- **Playbook version history with per-version changelog and usage** (4c) — a timeline of playbook versions, each with authored changelog bullets (typed by icon: added clause, position tightened, reworded) and "used in N matters" (with matter names for small counts), plus a `Compare to v<n>` action (target screen not drawn).
- **AI-drafted-content provenance markers** — throughout 2b/2c/3b, AI-suggested content is visually distinguished ("AI DRAFTED — NOT YET REVIEWED", "SUGGESTED", "Taken from <playbook>") and gated behind an explicit human accept action before being treated as final; this is a UI pattern (draft vs. saved state) with no current equivalent, since today's `CreateTemplateDialog` saves immediately.
- **Risk-distribution mini-bars** (1e header cells, 1a risk profile) — a small horizontal stacked bar (red/amber/green segments) summarizing risk distribution across a set of findings, both per clause-column (1e) and per matter (1a).

## 5. Visually/interactively demanding items (disproportionate implementation cost)

- **Split-pane review workspace with synced document viewer (1b)** — three resizable(?) panes; the right pane is a real PDF/document renderer (today via `PdfCanvas`/pdf.js per the current-app notes) that must scroll to and highlight the exact cited passage, support multiple source documents as tabs, and step between multiple evidence passages per finding ("Passage 1 of 2… Prev/Next") — i.e., synchronized citation-to-highlight-to-scroll across arbitrary PDFs, now multiplied across N documents in a collection rather than one document.
- **Tracked-changes / redline rendering (3a "84 edits", 3c "the workings")** — parsing DOCX tracked-change XML (insertions, deletions, and comments) well enough to render inline strikethrough/underline diffs plus threaded margin comments with author/date, and doing this across many documents to compute "6 redlines across 4 documents" statistics. This is a nontrivial document-diffing subsystem the current app has no code for at all (it only reads flattened text for clause extraction).
- **Variation trail / net-position synthesis (1d, 4a's staleness, 4b's diff)** — requires the model (or a deterministic merge step) to combine a base document with N amending documents into one coherent "net position" statement, per clause, and to detect when a later document's language "moves," "deletes," or "replaces" an earlier provision (shown as structured before/after facts: date moved from 2024→2026, notice period 12mo→6mo, condition deleted). This is genuinely a multi-document reasoning/diff problem, not just multi-document RAG.
- **Comparison grid at scale (1e)** — a dense table with per-cell rich content (risk dot, verification icon, full sentence) rather than truncated text; for a document set larger than the 4 rows shown (e.g. real portfolios of dozens or hundreds of leases) this needs virtualization, sticky headers, and possibly a "full text" toggle that reflows row heights — none of which is demonstrated beyond a 4-row static mock.
- **Inferred-position strength scoring & consistency detection (3b)** — clustering multiple redline instances of "the same" clause across documents, deciding whether they agree or conflict, and producing a natural-language rationale ("Struck twice, but signed twice without amendment — possibly a concession traded elsewhere rather than a position"). This is a nontrivial analytical/LLM pipeline, and the UI needs to gracefully represent partial/contradictory evidence, not just a binary.
- **Playbook drift/staleness tracking over time (4a/4b)** — needs a durable, queryable link between every "standard position" and every subsequent matter/document that tested it, aggregated into "held N of N," "conceded twice since," and "untested N months" — essentially an analytics layer over matter history keyed to playbook version and clause, plus scheduled/triggered "new turn arrived" changeset generation.
- **Playbook version diff/compare (4c "Compare to v3")** — referenced but not drawn; implies a structured diff view between two playbook versions (which clauses/positions/risk criteria changed) analogous to a code diff.
- **Global search (`⌘K`, 1a)** described as searching "matters, clauses, findings" — a cross-entity, keyboard-triggered command palette/search, which is a new subsystem (indexing of finding text, clause names, matter metadata) with no current analog.
- **Real-time/streaming states across three densities** — the redesign keeps (and multiplies) the current app's streaming-extraction UI (pulsing skeletons, spinners, "extracting…"), but now needs to render it consistently inside the ledger sidebar (1b), the brief cards (1c), the comparison grid cells (1e), and per-clause chips (2b) — four different layouts needing the same live-update wiring.

## 6. Data the app does not currently have

- **Matter entity** — a persistent object (id "24-0871", title, client name, counterparty, role, status, assigned fee-earner) distinct from a one-off run; today the app has no server-side/persistent run history at all beyond whatever is transiently in browser state (per README, likely local-storage-only, single-session).
- **Multi-document collections with typed relationships** — a document needs a `role` (BASE / VARIES / standalone) and collections need an ordered list of member documents with dates, so the app can compute "as varied by" chains. No such document-relationship model exists today (today's data model is flat: documents are inputs to one run, each document reviewed independently per row in the tabular view).
- **Per-finding verification/disposition state** — `unchecked | verified | flagged | rejected`, an assignee (user reference), a private note thread with author+timestamp, and an edit history ("Edited by you · 21 Aug 11:02"). Today a finding only has a risk level and the raw extracted text/citations — no workflow state, no ownership, no notes, no edit tracking.
- **User/identity and firm data** — named users ("R. Hume", "M. Okafor"), initials avatars, a firm name ("CH&P LLP"), "assigned to me" queries, and activity attribution ("You flagged…", "M. Okafor rejected…"). The current app (per README/settings) is single-user/local-only with an OpenRouter key — there is no multi-user auth, identity, or per-user assignment model at all.
- **Standard position per clause** — a new playbook-clause field, plus (for the "deviates" comparison) some structured way to compare a finding against it. Requires either a new prompt/JSON schema field or a genuinely new comparison LLM call.
- **Precedent-document corpus with tracked-changes/comments extracted** — DOCX-level tracked-change and comment data (who changed what, from what to what, and any margin comment text) per document, plus which documents are chained "turns" of the same negotiation. Nothing like this is ingested today (the current pipeline reads flattened document text for clause extraction only).
- **Inferred-position provenance & scoring data** — per inferred position: the list of source documents/redlines it derives from, a consistency count (e.g. "4 of 4"), and human decisions (adopted/reworded/rejected) recorded against it — an entirely new data model layered on top of the precedent corpus.
- **Playbook version history with changelog and usage counts** — versioned playbooks (v1…v4…) each with an authored changelog, an author, a date, and "used in N matters" (with matter names) — today templates appear to be a single mutable object with no version history at all.
- **Position staleness/drift tracking** — for each standard position, every matter/document since its last version that tested it, whether the position held or was conceded, and a "last tested" date + matter name. This requires linking findings back to the specific playbook clause/position version they were checked against, matter by matter, over time.
- **Changeset / proposed-version data** — a pending, unpublished set of proposed edits to a playbook (each tagged CONFIRM/DRIFT/NEW CLAUSE, with accept/decline state) that exists before a version is published — a draft-version concept with no current equivalent.
- **Global cross-entity search index** — matters, clauses, and findings all searchable together via `⌘K`.
- **Client-facing export/report** referenced repeatedly ("Export report", the `Report` segmented-control tab, "the report will mark them as unverified AI output") but never actually shown as a screen — implies a report-generation data model (which findings/verification states/notes make it into a client deliverable) that doesn't exist today (today's export is only "Export CSV" of the tabular grid).

## 7. Ambiguous or unbuildable as drawn

- **`Standard positions` top-level nav tab** (seen in 1a's header) has no screen anywhere in the file. It's presumably a cross-playbook browse/search view over every standard position (e.g. "show me every position on rent review across all playbooks"), but nothing indicates its layout, filtering, or relationship to the per-playbook "living playbook" page (4a). An implementer has to invent this screen from scratch.
- **`Compare` segmented-control tab** (1b header, next to `Review`/`Report`) is named but never shown. Given 1e is described as being for "genuinely separate documents," it's unclear whether `Compare` inside a single-collection review means something different (e.g. compare two runs, or compare this matter's findings to another matter) — the distinction between this and 1e is not drawn out.
- **`Report` segmented-control tab / "Export report" / "Export"** — three different affordances (1a's "Export report" button, 1b's segmented `Report` tab, 1b/1c/1e's `Export` buttons) that may or may not be the same feature (a live report *view* vs. a *generated file*). No exported-report screen is shown, so its structure, what "unverified AI output" marking looks like in the output, and whether `Report` opens a preview or triggers a download are all unspecified. (The doc's own "try next" prompts flag this gap themselves: "what does the exported client report look like?")
- **"Compare to v3" (4c)** — a playbook-version diff is referenced as an action but never rendered; an implementer must invent the diff visualization (side-by-side clause text? a changelog expansion? inline strikethrough like 3c's redlines?).
- **Settings/model configuration** — the current app's `SettingsPanel` (OpenRouter key, model dropdown, parallel-requests slider) has no redesigned equivalent at all; 1f mentions "Model: claude-sonnet-4 · change" as an inline link, implying settings may move inline/contextual rather than being a standalone page, but this is never confirmed with a dedicated screen.
- **How "deviates" is actually computed** — the UI assumes the system can reliably detect that a finding's extracted text conflicts with a stored standard-position text and generate a clean "WE ASK FOR" vs "THIS LEASE SAYS" comparison. Whether this is a separate LLM call, a prompt-embedded instruction, or a deterministic rule is undefined — the prototype only shows the resulting UI, not the mechanism, and gets no more specific than showing it always succeeds cleanly.
- **OCR flow (1f: "Scanned — running OCR, 40%")** — a progress percentage is shown for OCR of a scanned document, but there's no screen for OCR failure/low-confidence results, and the current app's `RunPanel` explicitly treats scanned files as a hard failure ("No text layer found" — file rejected outright), so this is a behavior change with no failure-path design.
- **Ambiguous-document resolution (3a "What is this?")** — three role chips are offered (THEIR DRAFT / OUR MARKUP / EXECUTED) but it's unclear whether a document can hold more than one role, what happens if the user skips classification, and how a wrongly-classified "chain" gets corrected later.
- **Keyboard-shortcut system** — `J` for "next unchecked" is shown in two places (1b, 2b) with no indication of a fuller shortcut scheme (verify/flag/reject bindings, prev, etc.) — an implementer has to decide the rest.
- **Multi-user concurrency/permissions** — activity feed and assignment imply multiple fee-earners work the same matter concurrently (flagging for each other, rejecting each other's findings), but there's no indication of real-time sync, conflict handling, or role-based permissions (e.g. can anyone publish a playbook version, or only certain roles?).
- **1b vs. 1c** are presented as alternatives for the same slot ("Alternative to 1c" / "Alternative to 1b") — the prototype doesn't resolve which one ships, and a real implementation would need to pick one (or build both, doubling review-screen cost) since they have materially different layouts (3-pane vs. single column with overlay PDF).
